# Development, Deployment and Recovery — Alpha

## Local development

Requires Node.js 22.16.0 or newer. `node:sqlite` is experimental in this runtime.

```sh
npm run check
npm test
npm start
```

Default listener: `127.0.0.1:3000`; database: `./data/workspace.sqlite`; public origin: `http://localhost:3000`. For a different host/port, set both `HOST`/`PORT` and `APP_ORIGIN` carefully. The first web visitor on a private instance can create the owner account—keep the initial listener confined to a trusted local environment. Password minimum is 12 characters.

## Container preview

```sh
APP_ORIGIN=http://localhost:3000 docker compose up --build -d
docker compose ps
curl -fsS http://127.0.0.1:3000/api/health
```

Named `workspace-data` volume stores SQLite. The container has a non-root user, read-only root filesystem, limited temporary storage, dropped Linux capabilities, and localhost-only host port binding. Verify writable volume ownership and health on the actual container host; no Docker runtime test was performed as part of initial source creation.

### Private HTTPS reverse proxy

For owner-managed remote access, terminate TLS at an audited reverse proxy. Point it to `127.0.0.1:3000`, preserve long-running `text/event-stream` connections, set `APP_ORIGIN=https://your-private-host.example`, and keep backend ports inaccessible on untrusted interfaces. Use strict HTTPS and suitable firewall/VPN rules; never directly expose this preview app as production internet service.

## Recovery and upgrade guidance

**Do not rely on a raw copy of an active SQLite database while WAL is active.** Use the consistent online snapshot command for a single SQLite database:

```sh
npm run backup -- --db ./data/workspace.sqlite --output ./backups/workspace-2026-11-03.sqlite
```

The command refuses to overwrite existing backups, uses the built-in SQLite online backup API, checks database integrity, copies any referenced attachment bytes to a sibling `BACKUP.sqlite.files` directory, verifies each against its SHA-256 and size in the saved snapshot, and saves files with restrictive permissions. A missing/corrupt attachment aborts the backup without publishing a completed snapshot. It does not encrypt the resulting database; handle it as sensitive. The source path must be a readable SQLite database and the backup target must be on a suitable writable local filesystem. If a custom `FILES_PATH` is configured for the server, supply `--files` for the matching attachment directory. In the Docker preview the `scripts` directory is not included, so run this tool with a compatible host Node runtime against a trusted database/volume copy or explicitly adapted maintenance container; do not expose the database or its keys over a network.

**Restore into an isolated new directory (never overwrite an installation):**

```sh
npm run restore -- --from ./backups/workspace-2026-11-03.sqlite --dest ./restored-test-instance
```

The restore command validates SQLite integrity and foreign keys, rejects nonempty WAL sidecars, verifies every referenced attachment against its recorded size and SHA-256, and creates a new directory containing `workspace.sqlite` and optional `workspace.sqlite.files/`. Missing or corrupt attachments stop the process before creating the destination. Existing directories are never overwritten; partial copies are cleaned up. Use only an offline snapshot generated by the backup command. Start a disposable test instance on a separate private port with `DATA_PATH=./restored-test-instance/workspace.sqlite` and a matching `APP_ORIGIN`. Validate sign-in, channels, messages, notes, tasks and private file downloads. The isolated Node integration tests exercise restoration and authenticated file access, but full host-level disaster recovery, encrypted/scheduled backups and production acceptance remain pending.

Changes to `src/server.mjs` schema require compatible, versioned migrations before upgrades are supported. Do not overwrite unknown preexisting data or promote this alpha to a production release.

## Authenticated encrypted snapshots and isolated restores

Use a strong unique passphrase in a regular private file outside the repository and archive destination (`chmod 600 /private/backup-key` on Unix; do not place it in command arguments, shell history, or source control).

```sh
npm run backup:encrypted -- --db ./data/workspace.sqlite --output ./backups/workspace.gcws --passphrase-file /private/backup-key
npm run restore:encrypted -- --from ./backups/workspace.gcws --dest ./test-restored --passphrase-file /private/backup-key
```

The `GCWSENC1` archive is a single authenticated AES-256-GCM envelope containing the SQLite snapshot and attached files, with a random 16-byte scrypt salt (`N=32768, r=8, p=1`), random 12-byte nonce, 16-byte GCM authentication tag, and signed manifest/file digests. On restore the entire archive is decrypted and authenticated in a private temporary directory **before** validation and creation of the exclusive, new destination. Wrong keys, tampering, truncated files, unsafe paths, and existing destinations are refused. There is no in-place restore.

**Residual risk:** the online snapshot, decryption, and integrity verification temporarily write **plaintext** to restricted OS temp storage (directories mode 0700 and files mode 0600 on Unix); removal does not guarantee forensic erasure. Use encrypted temporary storage and trusted local administration. Losing the key makes recovery impossible. The existing `backup` and `restore` commands still produce and consume **unencrypted** snapshots. Scheduling, offsite redundancy, secret escrow, retention policy, host-level recovery and production acceptance remain outstanding.

## Build and test gates

CI performs `npm run check` and `npm test` on Node 22.16.0. These cover syntax, first-user bootstrap, space permissions, message editing/replies/removal, authorization-scoped search, invitation use, owner revocation with live-stream closure, online backup integrity and origin rejection. They now include an isolated attachment restore-and-download test and owner invitation-revocation tests. They do not cover real browser visual interaction, mobile/native packaging, Docker runtime, accessibility audit, load, or production security acceptance.
